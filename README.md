## Задание 1. Алгоритм банкира

`python3 banker.py bank1.txt --check P1,P3,P4,P2,P0 < requests.txt`

- **Need = Max − Allocation.**
- **Проверка безопасности:** `Work = Available`; ищется незавершённый процесс с `Need ≤ Work`; он «завершается» и возвращает ресурсы: `Work += Allocation[i]`. Если завершились все — состояние безопасно.
- **request(pid, vector):** запрос > Need → ошибка; запрос > Available → процесс ждёт; иначе ресурсы выделяются пробно и проверяется безопасность; если состояние небезопасно — **откат**.

| Набор | Результат | Эталон |
|---|---|---|
| bank1 | SAFE, найдена последовательность P1, P3, P4, P0, P2 | безопасное, P1, P3, P4, P2, P0 |
| bank2 | UNSAFE | небезопасное |

Безопасных последовательностей может быть несколько. Алгоритм перебирает процессы по порядку номеров и нашёл P1, P3, P4, **P0, P2**; эталонная последовательность P1, P3, P4, **P2, P0** проверена отдельно (`--check`) — тоже **безопасна**. Вывод о безопасности совпадает с эталоном для обоих наборов.

Запросы к bank1 (обрабатываются последовательно):

| Запрос | Результат |
|---|---|
| P1 (1, 0, 2) | **ВЫДЕЛЕНО** — новое состояние безопасно (P1, P3, P4, P0, P2) |
| P4 (3, 3, 0) | **ЖДАТЬ** — свободно только (2, 3, 0) |
| P0 (0, 2, 0) | **ОТКАЗ** — после выделения состояние небезопасно, откат |
| P3 (3, 0, 0) | **ОШИБКА** — больше, чем оставшаяся потребность Need = (0, 1, 1) |

## Задание 2. Детектор по журналу событий

Журнал: строки `поток acquire|wait|release ресурс`. После каждого события строится **граф ожидания** (не граф распределения!): ребро T → U, если поток T ждёт ресурс, которым владеет U. Цикл ищется обходом в глубину с раскраской (серая вершина на текущем пути = цикл).

- `log_ok.txt`: T2 ждёт R1, пока его держит T1, — ребро есть, цикла нет → «Взаимоблокировок не обнаружено».
- `log_deadlock.txt`: после строки 7 — цикл **T1 → T2 → T3 → T1** (T1 ждёт R2 у T2, T2 ждёт R3 у T3, T3 ждёт R1 у T1).

## Задание 3. TrackedLock и deadlock.py

**Как убедиться, что программа с deadlock зависла:** `python3 deadlock.py plain`. Оба потока печатают «захватил …, жду …», и дальше ничего не происходит (процесс не нагружает процессор — потоки спят в ожидании блокировки). Через 3 с `faulthandler.dump_traceback_later` печатает стеки всех потоков и завершает процесс: T1 и T2 стоят на строке 25 (`with second:`), главный поток — в `join()`.

**TrackedLock** (`python3 deadlock.py tracked`): перед блокирующим ожиданием поток добавляет ребро «я → владелец блокировки» в общий граф ожидания и проходит по цепочке владельцев. Если цепочка возвращается к нему — бросается `DeadlockError`:
`T2: DeadlockError — цикл ожидания: T2 ждёт lock_a, её держит T1; T1 ждёт lock_b, её держит T2`.
T2 выходит из `with` и освобождает lock_b, T1 доделывает работу, программа завершается нормально.

**Исправление** (`python3 deadlock.py ordered`): оба потока захватывают блокировки в одном порядке (lock_a, затем lock_b). Нарушено условие **циклического ожидания**.

## Задание 4. Обедающие философы

5 философов, 5 секунд на вариант. Сторож объявляет deadlock, если 2 секунды никто не ел.

| Вариант | Результат | Сколько раз поел (Ф0…Ф4) | Всего |
|---|---|---|---|
| Наивный (левая, затем правая) | **DEADLOCK** | 0 / 0 / 0 / 0 / 0 | 0 |
| Нумерация вилок | 5 с без зависаний | 228 / 355 / 393 / 450 / 228 | 1654 |
| Официант (4 места) | 5 с без зависаний | 409 / 402 / 408 / 403 / 406 | 2028 |

- **Наивный:** каждый взял левую вилку и ждёт правую — замкнутый круг из 5 философов.
- **Нумерация:** сначала берётся вилка с меньшим номером. Ф4 берёт сначала вилку 0, а не 4, — круг разорван. Но распределение неравномерное: Ф0 и Ф4 конкурируют за вилку 0 как за первую и едят реже (228 против 450).
- **Официант:** за столом не больше 4 философов — хотя бы один из них гарантированно получит обе вилки (принцип Дирихле), поэтому круг не замкнётся. Здесь и больше всего приёмов пищи, и самое честное распределение (402–409).
- Пауза между взятием вилок (`sleep`) нужна только чтобы deadlock в наивном варианте воспроизводился надёжно. Исправления работают за счёт порядка/ограничения, а не за счёт `sleep`.

## Четыре условия взаимоблокировки

1. Взаимное исключение. 2. Удержание и ожидание. 3. Отсутствие принудительного освобождения. 4. Циклическое ожидание.
Упорядоченный захват, нумерация вилок и официант нарушают **условие 4**. `TrackedLock` не предотвращает, а **обнаруживает** цикл и выводит из него один поток (он сам освобождает свои ресурсы).

## Контрольные вопросы

**1. Почему упорядочивание захвата ресурсов исключает deadlock?**
Если все потоки захватывают ресурсы строго по возрастанию номеров, то поток, ожидающий ресурс j, держит только ресурсы с номерами меньше j. В цикле ожидания номера ресурсов вдоль цепочки должны строго возрастать — и цепочка не может вернуться к первому ресурсу. Значит, циклического ожидания не бывает, а без него deadlock невозможен.

**2. Почему алгоритм банкира редко применяется в универсальных ОС?**
Он требует заранее знать **максимальную потребность** каждого процесса во всех ресурсах — в обычной ОС это неизвестно. Число процессов и ресурсов постоянно меняется, а проверка безопасности при каждом запросе стоит O(m·n²). Кроме того, алгоритм осторожен: отказывает и в запросах, которые на практике не привели бы к deadlock, — ресурсы простаивают. Поэтому ОС используют упорядочивание блокировок (например, lockdep в ядре Linux), обнаружение или просто игнорируют проблему.
